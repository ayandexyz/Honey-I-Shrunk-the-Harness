# jcode-sdk shim contract — apps/desktop backend

Full plan + contract for wiring `apps/desktop` to freecode's `apps/core`
instead of Jcode's real backend. CLAUDE.md/AGENTS.md's "Desktop App" section
is a short pointer to this doc, not a copy — this is where the detail (and
the per-item Status tracking) lives, kept out of the main agent guide so it
isn't reloaded every turn.

Shipping it (packages, signing, auto-update, the download page): see
`2026-10-27-honey-desktop-release.md`.

## Background

The native desktop frontend is vendored from
[jcode-desktop](https://github.com/1jehuang/jcode-desktop) (MIT) via `git
subtree` into `apps/desktop` — not a submodule or one-time copy, so it keeps
upstream's history and can pull upstream's future commits. It replaced the
old Tauri/React `apps/web-app` (retired, commit `21dc2260`), which also used
to be what `apps/core/web-server.ts` served to phones/browsers — that path
404s until this app (or something else) ships a replacement bundle.

Stack: Rust, not TypeScript — a GPU-accelerated native UI (`gpui`) across 9
workspace crates (`jcode-desktop-ui`, `-ui-core`, `-harness`, `-motion`,
`-voice`, `-accounts-ui`, `-api`, `-updater`, `-model`). Doesn't go through
`packages/shared` or the Node/bun toolchain — a fully separate build
(`cargo`, not `pnpm`).

## The real integration point — corrected 2026-10-26

An earlier note claimed only `crates/jcode-desktop-api` needed to diverge
from upstream. **That was wrong** — `jcode-desktop-api` turned out to be
unrelated window-launch plumbing. The actual coupling to Jcode's backend is
much deeper:

- Every desktop crate depends on **`jcode-sdk`** (~8,400 lines) and its own
  4 sub-crates (`jcode-harness-api`, `jcode-applet-types`,
  `jcode-provider-metadata`, `jcode-transport` — ~7,800 more lines
  combined), currently a **path dependency on a sibling `jcode` checkout**
  (`../../../jcode/crates/...` from each `Cargo.toml` — doesn't build
  standalone; needs a local `jcode` checkout — since Phase 2 via the
  generated `apps/jcode` overlay, see "Build + run").
- `jcode-desktop-harness` (~9,400 lines, `harness.rs` alone 4,084) directly
  orchestrates `jcode_sdk::JcodeClient` for session lifecycle, turn
  submission/retry, SSH remote transport, and managed-cloud provisioning.
- `jcode-desktop-ui` imports `jcode_sdk` types **directly in ~50 files**
  (`panel.rs`, `workspace.rs`, `sidebar_*.rs`, …) — not cleanly isolated
  behind the harness.

**Chosen approach — a drop-in `jcode-sdk` shim, not a UI rewrite.** Write a
new crate named `jcode-sdk` with `jcode_sdk::client.rs`'s same public types
and `JcodeClient` method signatures (`connect`, `create_session`, turn
submission, `EventStream`, `TurnResult`, …), but have its internals speak
freecode's JSON-RPC to `apps/core` (`packages/shared/src/ipc/protocol.ts` —
`METHODS`, `StreamEvent`) instead of Jcode's own socket protocol. If the
shim's surface matches closely enough, `jcode-desktop-harness` and the ~50
UI files need **no changes at all** — only what's underneath `JcodeClient`
changes. This is what keeps `git subtree pull` useful long-term: upstream
only ever touches UI/harness files we never modify, so pulls should stay
close to conflict-free. The *only* crate that's permanently "ours" and
never comes from upstream is this `jcode-sdk` shim.

## Phased plan

1. **✅ COMPLETE 2026-10-26 — the contract is fully listed.** Every
   `JcodeClient` method, `ApiEvent` variant and jcode crate `apps/desktop`
   uses is in the tables below, with desktop call counts. Rows marked
   "decide" are scope decisions for Phases 4–6, not unknowns. Hand-off to
   Phase 2: stub every row (including "signature only" ones) and re-export
   the `jcode_sdk` types unchanged.

   How it was done — read `jcode-sdk/src/client.rs` fully; map each
   method/event to freecode's `METHODS`/`StreamEvent`, flag gaps both
   directions. Produced the contract tables below. **Second pass, same day**:
   the first pass mapped what `client.rs` *offers*; the contract is what
   `apps/desktop` *uses*. Re-derived from desktop call sites — see
   "Phase 1 findings" below. It added 10 used methods and 13 consumed events
   the first pass missed, reversed one `cut` (`MessageAccepted`), and found
   coupling outside `jcode-sdk` entirely (`jcode_base`, disk session reads).
2. **✅ COMPLETE 2026-10-26 (branch `phase-2-desktop`) — `apps/desktop`
   builds against our stub `jcode-sdk` with zero edits to the subtree.**
   - **Shim** `apps/desktop-shim/jcode-sdk/`: a copy of upstream jcode-sdk
     whose `client`, `launch`, `launch_upgrade`, `ssh`, `auth` and
     `auth/callback` function bodies are `todo!("jcode-sdk shim: <fn>")`
     (215 stubs), generated by `apps/desktop-shim/stub_bodies.py`. Trait
     impls (`Drop`, `Default`, `Clone`, `Iterator`) and `const fn`s keep their
     bodies. The pure modules (`errors`, `collections`, `turn_retry`,
     `worktrees`, `structured`, `diagnostics`) and every type re-export are
     upstream verbatim, so the public surface is identical **by
     construction** — signature drift is impossible, not just checked.
     `#![allow(unused, dead_code)]` in `lib.rs` until Phase 3 replaces the
     internals.
   - **Overlay, not `[patch]`**: Cargo's `[patch]` cannot override a *path*
     dependency, so the plan's original mechanism was unworkable.
     `scripts/desktop-overlay.sh` regenerates `apps/jcode/` on every run:
     each `crates/<name>` symlinks into the real checkout
     (`apps/jcode-upstream`, or `$JCODE_UPSTREAM`), except
     `crates/jcode-sdk` → `../../desktop-shim/jcode-sdk`. Cargo resolves
     path deps lexically (verified with `cargo metadata`: `jcode-sdk` →
     `apps/jcode/crates/jcode-sdk/Cargo.toml`), and no jcode crate uses
     workspace inheritance, so per-crate symlinks need no root manifest.
     Nothing else in jcode depends on `jcode-sdk`, so the swap is isolated.
   - **Verified**: `cargo build -p jcode-desktop` exit 0; the binary contains
     the stub strings (`jcode-sdk shim: send_message_with_reminder`). Not
     yet run end to end: launching it while another `jcode-desktop` is open
     hands off to that instance and exits.
   - **What it surfaced**: no compile-time leaks — expected, since the
     surface is upstream's own. The leaks are the runtime ones Phase 1
     already found (permission replies, `MessageAccepted`, `jcode_base` disk
     reads); the harness tests still compile, against Jcode's frame protocol
     (finding 6).
3. **✅ COMPLETE 2026-10-26 (branch `phase-2-desktop`) — the shim speaks
   freecode JSON-RPC to a real `apps/core`; the desktop sidebar lists
   freecode's sessions.**
   - **Transport** `apps/desktop-shim/jcode-sdk/src/freecode.rs`: core is a
     child process, newline-delimited JSON-RPC 2.0 on its stdio; a reader
     thread routes replies to callers by `id` and stream events (lines with
     `type`) to `EventStream` subscribers, filtered by session. The event
     *translation* (`translate_event`) returns `None` for everything —
     that table is Phase 4.
   - **One shared core per desktop process.** The harness opens a fresh
     `JcodeClient` per session-list refresh (every few seconds), so a core
     per client would be a Node boot per refresh. Clients are handles on a
     process-global `Inner`; a dead core is respawned by the next `connect`.
   - **Finding core** (`locate_core`): `FREECODE_CORE` (`.js` → `node`,
     else `<bin> serve`) → the repo's `apps/core/dist/server.js` when the
     desktop binary is inside the monorepo (dev: core and desktop change
     together, as the TUI does) → `freecode` on `PATH`.
   - **Done rows**: `connect`, `launch` (= connect to the shared core),
     `ensure_runtime` (only checks core can be found — core is spawned on
     first connect), `socket_accepts` (`false`, so the harness never tries
     to revive a Jcode daemon), `events`/`next`/`next_timeout`,
     `is_closed`, `supports` (no capabilities advertised), `ping`
     (`config.get`), `list_sessions`/`list_sessions_limited`
     (`session.list`, every project, newest first, truncated in the shim).
     Session mapping: `id`→`session_id`, `projectPath`→`working_dir`,
     `archived` status→`archived: true`, `updatedAt`/`lastTurnAt`→
     `updated_at_ms`/`last_active_at_ms`; `status` is always `idle` (freecode's
     status is lifecycle, jcode's is runtime activity).
   - **Core lifetime — the one `apps/core` change** (`server.ts`): core now
     shuts down gracefully (exit 0) when stdin reaches EOF, after answering
     in-flight requests. `PR_SET_PDEATHSIG` alone was not enough: it fires
     when the spawning *thread* exits (so core is spawned from its own
     long-lived thread), and a core whose parent died could still survive —
     observed: an orphan from a finished test held the test's stderr pipe
     for 8 minutes. EOF covers every way a client goes away, including
     SIGKILL. `serve` is stdio-only (web/mobile use `startWebServer`), so
     EOF really means no client. Jcode never faced this: its daemon is
     spawned *detached* and meant to outlive the desktop, and private
     instances are stopped by `Drop` (SIGTERM → 3s → SIGKILL).
   - **Fixed from Phase 2**: `user_jcode_home`, `home_dir` and
     `user_app_config_dir` are pure path helpers, not daemon code; their
     upstream bodies are restored (startup panicked on the first).
   - **Verified**: shim unit tests (2) + live test
     `tests/freecode_core.rs` (`--ignored`: connect, ping, list, second client
     reuses the core); the desktop built and run in an isolated instance
     (own `XDG_RUNTIME_DIR`) showed freecode sessions grouped by project, one
     core for the whole run (`jcode-sdk shim: started freecode core pid=…` in
     the desktop log), and that core exited on its own after the desktop was
     SIGKILLed; `echo '{…session.list…}' | tsx apps/core/src/server.ts`
     answers then exits 0.
   - **Still open, by design**: the "New session" panel sits at "Starting
     session" — `create_session` and the event translation are Phase 4.
     The installed release (0.47.1) predates the EOF fix; until the next
     release, only the repo core shuts down on EOF.
4. **IN PROGRESS (branch `phase-2-desktop`) — shim + approve card built and
   verified through the shim; what is left is a human driving one turn in
   the GPUI window (see "Not yet verified" below).**
   - **Turns** (`freecode_session.rs`): jcode's send is fire-and-forget,
     core's `session.send` answers when the turn ends. The shim leaves the
     request in flight, publishes `MessageAccepted` + `SessionStatus(running)`
     at once, and a watcher thread turns a failed reply into
     `TurnStopped(Failure)` + `Error` only if nothing closed the turn first.
     Steering (`soft_interrupt_with_images`) is `session.send` with
     `streamingBehavior: "steer"`, answered synchronously as the harness
     expects. `cancel` = `session.stop`, and the next `done` becomes
     `TurnStopped(Interrupted)`.
   - **Events** (`freecode_events.rs`, stateful per session):
     `text_delta`→`TextDelta`; `thinking_delta`→`ReasoningDelta`, with
     `ReasoningDone` synthesized at the first non-reasoning event;
     `tool_start`→`ToolStart`+`ToolExec`; `tool_complete`→`ToolDone`
     (`error` = result when `success: false`); `usage_totals`→`TokenUsage`
     (run totals, not jcode's per-call — context-size readouts will run
     high); `done`→`TurnDone`+`SessionStatus(idle)`;
     `session.error`→`TurnStopped(Failure)`+`Error`+idle;
     `turn_started`→running; `compaction_*`→`compacting`/back;
     `permission_asked`→`PermissionRequest`. `text`/`thinking` snapshots and
     `tool_output` are dropped (the deltas and `ToolDone` already carry
     them); core lines without a `sessionId` (`mcp.server.*`) are ignored.
   - **Scoping**: `Error` has no session id, and one shared core serves
     every panel, so each client binds its subscriptions to the session it
     attached to or created (`attach_to`) and session-less events are
     published with a target session — an error shows in its own panel only.
   - **History**: `attach_session` = `session.resume`, whose transcript is
     cached for the `get_history_with_images` call that follows. User and
     assistant text only (the UI drops tool rows anyway); harness-written
     user messages are hidden except steers; images not mapped yet.
   - **Runtime info**: provider/model/auth from `config.get`, routes from
     `models.list` for the current provider. `set_model` takes
     `provider:model` (the desktop's explicit-route form) or a bare id on
     the current provider → `config.setCurrentModel` (per process, not per
     session).
   - **Permissions** (decision 2026-10-26: build an approve UI, not
     auto-allow): `permission_asked` passes through as `PermissionRequest`,
     and `respond_to_permission` maps jcode's `Allow`/`AllowAlways`/`Deny`
     to core's `allow-once`/`allow-always`/`deny` via `permission.answer`.
     **The approve card** (`jcode-desktop-ui/src/panel_permission_card.rs`,
     a freecode addition — upstream Jcode never asks, so its desktop only
     played a sound): a per-panel queue of pending requests (deduplicated by
     id, cleared when the turn ends), rendered in the composer dock above the
     prompt queue as "Allow `<tool>`?" + the description and three pills,
     Deny / Always allow / Allow, styled like the applet consent card.
     Upstream hooks kept minimal: `panel.rs` (module, field, init, one line
     in `apply_event`), `panel_composer.rs` (one child), `harness.rs`
     (`Command::RespondPermission` → `SessionCommand::RespondPermission` →
     `client.respond_to_permission`, failures as `CommandFailed`). Verified
     live through the shim (`tests/freecode_permission.rs`, MiniMax-M3):
     `MessageAccepted → SessionStatus → PermissionRequest(bash) → [Allow] →
     ToolStart → ToolExec → ToolDone("freecode-permission-ok") → TextDelta… →
     TurnDone`, 6s. **Gotcha found doing it**: a user `PermissionRequest`
     hook runs *before* core emits `permission_asked` — agent-fold's (305s
     timeout) held every ask for 5 minutes, so the card only ever saw
     leftovers. Removed from `~/.freecode/settings.json` on this machine
     2026-10-26 (backup `settings.json.bak-agent-fold-hooks`); with such a
     hook installed, the card is the fallback after it.
   - **Unsupported, not panicking**: every other `JcodeClient` method the
     harness can reach (`rename_session`, `set_session_saved`,
     `set_reasoning_effort`, `send_system_reminder`, `rewind`,
     `rewind_undo`, `transfer_session`, `clear`, `runtime_command`,
     `background_tool`, applets, todo, auth notifications) returns a clean
     `UnknownRequest` error the harness already renders, instead of a
     `todo!()` that killed the session worker.
   - **Verified**: 8 shim unit tests; live `tests/freecode_turn.rs` on
     MiniMax-M3 — events `MessageAccepted → SessionStatus → TextDelta("pong")
     → TokenUsage → TurnDone`, history `user/assistant` round-trips. The
     failure path was verified by accident first (expired OpenAI OAuth):
     `MessageAccepted → SessionStatus → TurnStopped → Error`. **Not yet
     verified in the GPUI window**: the draft panel creates its session
     only when a prompt is submitted, which needs a human at the keyboard.
5. **DEFERRED 2026-10-26 (user decision: get the desktop running first).**

## Phase 1 findings (call-site audit)

Method: every `JcodeClient` method and `ApiEvent` variant counted at its
call/match sites in `apps/desktop/{crates,src}`, test files excluded
(`*_test(s).rs`, `tests/`, fixtures). Numbers are production sites.

1. **The client seam is one file.** Every production `JcodeClient` call is
   in `jcode-desktop-harness/src/harness.rs` (plus `notify_auth_changed` /
   `set_reasoning_effort` in `managed_cloud_parity.rs`). The ~70 UI files
   that import `jcode_sdk` use its **types** (`SessionInfo`,
   `HistoryMessage`, `ApiEvent`, `ModelRouteInfo`, `RenderedImage`,
   `TurnStopReason`, …), never the client. So the shim must reproduce those
   types byte-compatibly (re-export them, don't redefine them), and its
   behaviour only has to satisfy `harness.rs`.
2. **The desktop never answers a permission prompt.** `PermissionRequest` is
   matched only to route it to a session and to play a sound
   (`sound_events.rs`); `respond_to_permission` has zero callers. Jcode runs
   tools without asking. Against `apps/core` a `permission_asked` would
   block the turn until core's 30-minute prompt timeout (treated as DENY).
   Decision needed before Phase 4: run desktop sessions in a mode that
   never asks, auto-answer in the shim, or add an approve/deny UI (a change
   to upstream files — conflicts on every `subtree pull`).
3. **`MessageAccepted` is not cuttable** — 14 production matches. The
   harness's submit flow waits on it. The shim must synthesize it as soon
   as core accepts `session.send`, before any stream event.
4. **The desktop reads Jcode's session store off disk**, bypassing the
   client entirely, through `jcode_base::session`:
   `persisted_history.rs` (`Session::load_from_path`,
   `render_messages_and_images`), `workspace_resume.rs`
   (`Session::create_with_id`, `render_messages`, `session_presence`),
   `resume_content_search.rs` (journal path), `workspace.rs`
   (`streaming_session_ids`), `panel.rs` (`session_path`). A shim over
   `JcodeClient` cannot reach these; with it in place, resume/history/search
   would show Jcode's sessions under `~/.jcode`, not freecode's under
   `~/.freecode/sessions`. These need their own replacement (see "Beyond
   jcode-sdk").
5. **The first pass got these rows wrong**: `MessageAccepted` (cut → needed);
   `list_models`, `list_sessions`, `get_history`, `archive_session`,
   `send_message`, `create_session_with_options`, `respond_to_permission`
   have **zero** production callers (the used forms are
   `list_sessions_limited`, `get_history_with_images`,
   `send_message_with_reminder`, `create_session`); `TextReplace`/`TextDone`
   are never matched, so text needs only delta translation; `Compacted` is
   never consumed (only routed). Events that appear only in `harness.rs`'s
   `event_session_id` routing match (`Files`, `FileContent`, `FileStatus`,
   `TextMatches`, `History`, `Models`, `Sessions`, `TodoState`, …) are not
   consumed and need not be emitted.
6. **Harness tests speak Jcode's wire protocol** (`ClientFrame`/
   `ServerFrame`/`read_frame`/`write_frame` in six `harness_*_tests.rs`, 77
   sites). They fake a Jcode server, so they will test the shim's old
   transport, not freecode's. Phase 2 should expect them to fail to build or
   to test nothing real; decide to cut or port them, don't chase them.

## How to use this doc

- Before writing the shim crate (Phase 2+), walk this table top to bottom and flip `todo` → `stub` as each method gets a `todo!()` placeholder with the right signature.
- When actually implementing a method, flip `stub` → `done`.
- If a `cut` row turns out to matter, flip it back to `todo` and note why in this doc, not just in a commit message — the row is the tracking unit.
- Keep this doc in sync with the parent plan in CLAUDE.md's "Desktop App" section; that section should stay a short pointer here, not duplicate the table.
