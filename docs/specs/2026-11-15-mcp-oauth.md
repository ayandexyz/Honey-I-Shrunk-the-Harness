## 1. Problem

A remote MCP server that requires a login cannot be used at all, and nothing says so.

`mcp/transport.ts` `createHttpTransport` passes only static `headers`. A server that
answers `401` + `WWW-Authenticate: Bearer resource_metadata=…` fails `connect()`,
`mcp/init.ts` `connectServer` catches it, emits `mcpServerError`, and returns `null`.
The server's tools never appear. Measured 2026-11-15 against the owner's own config:

```
POST https://mcp.figma.com/mcp  (initialize, no token)
→ HTTP/2 401
  www-authenticate: Bearer resource_metadata="https://mcp.figma.com/.well-known/oauth-protected-resource",
                    scope="mcp:connect", authorization_uri="https://api.figma.com/.well-known/oauth-authorization-server"
```

Because `mcp/claude-code-config.ts` imports Claude Code's servers, the user did not
even add this server to FreeCode — it arrives from `~/.claude.json`, works in
Claude Code, and silently does nothing here. The same holds for every hosted server
that requires a login (Figma, Linear, Notion, Sentry, GitHub's remote server, …).
Claude Code, Codex and pi all support MCP OAuth; FreeCode has no OAuth code under
`mcp/` and no backlog entry for it.

## 2. Goals and non-goals

**Goals**
1. A remote server that needs a login is **reported as needing one** (`needs-auth`),
   never as a generic failure and never silently.
2. `freecode mcp login <name>` signs in with the browser (authorization code + PKCE,
   loopback redirect, paste fallback over SSH), and every later start connects
   without a prompt, refreshing tokens as needed.
3. `freecode mcp logout <name>`; `freecode mcp list` / `status` show the auth state.
4. Works for Claude Code-imported servers as well as FreeCode's own.

**Non-goals (this spec)**
- **Client ID Metadata Documents (CIMD).** pi serves its own at `https://pi.dev/oauth`;
  FreeCode has no hosted domain. Dynamic client registration (DCR) + static client ids
  cover the servers that matter. Revisit if a server supports CIMD only.
- **Enterprise IdP flows** (Claude Code's `xaa*.ts`), OS keychain storage, the legacy
  SSE transport.
- **Importing Claude Code's MCP tokens.** See §4.3.

## 3. Prior art: what to copy, what to skip

| Decision | pi | Claude Code | Codex | FreeCode |
|---|---|---|---|---|
| Who starts the browser flow | Only an explicit sign-in (`/mcp`), never a connect | Explicit `/mcp`, or the model via the `authenticate` pseudo-tool | `codex mcp login` | **Explicit only** (§4.1); pseudo-tool in Phase 2 |
| Where tokens live | `<agent-dir>/mcp-auth.json`, keyed `server|url` | OS secure storage, `mcpOAuth[serverKey]` | credential store (keyring or file) | `~/.freecode/mcp-auth.json`, `0600`, keyed `name|url` |
| Refresh concurrency | One in-process refresh promise + cross-process lockfile, held from read to save | Re-reads fresh storage before writing | `refresh_lock.rs`, `store_lock.rs` | Both, as pi (§4.4) |
| Redirect | `127.0.0.1` loopback, reuses the registered port | random port in 49152–65535, `MCP_OAUTH_CALLBACK_PORT` | loopback | `startCallbackServer` (ephemeral), reuse the registered port (§4.2) |
| Scope step-up (`insufficient_scope`) | New sign-in, never a refresh | — | — | Same as pi: report `needs-auth` |
| Request timeout to the auth server | 15s | — | — | 15s |

The rule all three share, and the one this spec is built around: **a connection
never opens a browser.** FreeCode's core is a daemon serving several frontends and
unattended `freecode night` runs; a browser that pops up because some imported server
connected in the background is wrong in every one of those contexts.

## 4. Design

### 4.1 Connection path (`mcp/init.ts`, `mcp/transport.ts`)

`createHttpTransport` gains an optional `fetch`. For a `type: "remote"` server
**without** an `Authorization` header in `headers` and **with** a stored sign-in,
`connectServer` passes `createAuthFetch` (`mcp/oauth/auth-fetch.ts`): it sends the
stored token, refreshes pre-emptively near expiry, and on a `401` refreshes once
under the lock (§4.4) and retries; when no refresh can help it throws
`McpNeedsAuthError`. With no stored sign-in nothing changes — a server that needs
no auth connects exactly as today, and one that does answers `401`.

**Not the SDK's `authProvider` transport option** (this section's first draft). On a
`401` the transport runs the SDK's whole `auth()` orchestrator, which for a server
with no stored client performs dynamic client registration and then calls
`redirectToAuthorization` — a background connect would register a new OAuth client
at the server on every daemon start (`client/auth.js` `authInternal`). Its refresh
also runs outside our cross-process lock. pi makes the same split: connections send
and refresh tokens; only an explicit sign-in (`mcp/oauth/login.ts`) runs `auth()`.

`connectServer` maps both to a new state rather than a generic error:

- `BusEvents.mcpServerNeedsAuth(name, url)` — a new bus event, carried to frontends
  like `mcpServerError`. The TUI renders a single line naming the fix:
  `figma needs a login — run: freecode mcp login figma`.
- The server's status is recorded as `needs-auth` so `freecode mcp list|status` can
  show it. Not cached across processes (Claude Code keeps a 15-minute
  `mcp-needs-auth-cache.json` to skip doomed connects; FreeCode connects at daemon
  start only, so the cost of one failed `initialize` per start is not worth a cache).

### 4.2 Sign-in (`mcp/oauth/login.ts`, `cli/commands/mcp/login.ts`)

`freecode mcp login <name>`:
1. Resolve the server from the merged config (own + Claude Code). Refuse a stdio
   server and a remote server with a static `Authorization` header.
2. Start the loopback listener (`startCallbackServer`). If a client is already
   registered for this server, ask for **its registered port** first — a registered
   client cannot use another redirect URI (pi `signInMcpServer`). If that port is
   taken, register a new client on an ephemeral one.
3. Run the SDK's `auth(provider, { serverUrl, resourceMetadataUrl, scope })` with an
   **interactive** provider whose `redirectToAuthorization(url)` prints the URL and
   opens the browser. Discovery (RFC 9728 protected-resource metadata → RFC 8414
   authorization-server metadata), DCR (RFC 7591), PKCE S256 and the RFC 8707
   `resource` parameter are all the SDK's.
4. Wait for whichever comes first: the browser callback, or a pasted redirect URL
   (SSH case; `parseAuthCodeInput`-style parsing, `state` must match, origin + path
   must match the redirect URI exactly).
5. `auth(provider, { authorizationCode })` exchanges the code; the provider saves
   tokens + `expires_at`. Print `Signed in to figma (scope: mcp:connect)`.
6. A running daemon picks the server up on its next start (Phase 1 — `freecode mcp
   start <name>` connects in its own process, so it verifies the sign-in but does not
   reach the daemon) or automatically (Phase 2, §7 Q2).

**Token endpoint auth method** (found live). DCR names
`token_endpoint_auth_method: "none"` whenever the authorization server lists
`none` (or lists nothing), as Claude Code does; otherwise it names none and takes
the secret the server issues (Figma lists only `client_secret_*`). Leaving it unset
everywhere — the first build — gets a secret by RFC 7591's default
(`client_secret_basic`), which a public-client-only token endpoint rejects as
`invalid_client`; the SDK then wipes the client and retries, surfacing only
"Existing OAuth client information is required". `login.ts` now names that cause.

Optional per-server config, for servers without DCR (GitHub's remote server, Slack):

```json
{ "name": "github", "type": "remote", "url": "https://api.githubcopilot.com/mcp/",
  "oauth": { "clientId": "…", "clientSecret": "${GITHUB_MCP_SECRET}", "scope": "repo", "callbackPort": 8765 } }
```

`clientSecret` goes through `expandEnvVars` (already used for Claude Code entries), so
a secret never has to be written into `config.json`. Claude Code's equivalent fields
on imported servers (`oauth.clientId`, `oauth.callbackPort`) are mapped by
`toMcpServer`.

### 4.3 Storage (`mcp/oauth/store.ts`)

`~/.freecode/mcp-auth.json`, mode `0600`, re-`chmod`ed on every write (the
`auth-store.ts` rule: `mode` only applies at creation). **A separate file from
`auth.json`:** the shape differs (client registration, tokens, PKCE verifier,
discovery state per server), and `auth.json`'s readers are typed per provider.

```json
{ "figma|https://mcp.figma.com/mcp": {
    "client": { "client_id": "…", "client_secret": "…", "redirect_uris": ["http://localhost:53122/callback"] },
    "tokens": { "access_token": "…", "refresh_token": "…", "scope": "mcp:connect", "token_type": "Bearer" },
    "expiresAt": 1763200000000,
    "codeVerifier": "…"            // only between steps 3 and 5 of §4.2
} }
```

Keyed by **name and URL** (pi `storeKeys`): two configs pointing at one URL keep
separate accounts, and changing a server's URL never sends its old token to the
new host.

**Never import Claude Code's MCP tokens**, even though the server definitions are
imported. Authorization servers commonly rotate refresh tokens, so two clients
refreshing the same grant log each other out — the reason the OpenAI OAuth spec
never imports `~/.codex/auth.json`. FreeCode registers its own client and holds its
own grant.

Tokens never enter the rollout log, OTLP export, logger output or a tool result. Only
`mcp.auth` events with `{ server, outcome }` are recorded.

### 4.4 Refresh

- **Pre-emptive:** `tokens()` refreshes when `expiresAt - 30s <= now`; a failed
  pre-emptive refresh falls through and lets the `401` decide (pi).
- **On 401:** the SDK calls `auth()` → refresh with the stored refresh token.
- **One refresh per server per process:** a shared in-flight promise.
- **One refresh per server across processes:** the daemon, `freecode run` and
  `freecode night` can all hold the same server. An exclusive-create lockfile
  (`mcp-auth-refresh-<sha256(key)[:16]>.lock`, `O_EXCL` as in
  `memory/consolidation-lock.ts`), stale after 20s, held **from reading the
  tokens to saving the new ones**. Inside the lock, re-read: if the access token
  changed since the request failed, another process already refreshed — use it.
- A refresh the server answered is always saved, even if the caller gave up —
  the old refresh token may already be dead.
- 15s timeout on every request to the authorization server.

### 4.5 Logout and status

- `freecode mcp logout <name>` deletes the entry (tokens **and** the registered
  client). Revocation (RFC 7009) is best-effort and only if the metadata advertises a
  `revocation_endpoint`.
- `freecode mcp list` gains an auth column: `—` (no auth), `signed in`,
  `needs login`, `expired (refreshes on use)`.

## 5. Risk: servers that only accept known clients

Figma's metadata (fetched 2026-11-15) advertises DCR
(`registration_endpoint: https://api.figma.com/v1/oauth/mcp/register`), no CIMD, and
confidential-client auth only (`client_secret_basic` / `client_secret_post` — so DCR
must return a secret, which §4.3 stores). Figma's documentation describes its remote
server as working with listed clients; **if its DCR refuses unknown client names,
the design is sound but Figma specifically will not work**, and the static `oauth`
config (§4.2) cannot fix it without a Figma-issued client. Phase 0 settles this
before any code.

**Tests (Phase 1):** store (0600, keying by name+URL, corrupt-file-is-empty);
provider (pre-emptive refresh, 401 refresh, refresh failure → needs-auth, a
concurrently-rotated token is reused, never `redirectToAuthorization` from the
non-interactive provider); callback and paste parsing (`state` mismatch, wrong path,
`error=` param); and one end-to-end test against a local fake — an HTTP server
serving protected-resource + auth-server metadata, `/register`, `/authorize`
(auto-approving), `/token`, and an MCP endpoint returning `401` until a valid token
arrives. No live network in tests.

**Evals:** none. This changes connectivity, not what the model does with a given
tool set, so the `eval ab` rule does not apply. Phase 2 adds a tool the model can
call; that phase needs a trajectory case (`needs-auth` server present → the model
offers the login instead of failing silently).
